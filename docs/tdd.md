# テスト駆動開発とテストリスト

このハンズオンでは，すべての機能をテスト駆動開発(TDD)で作る．
ここでは，どのIterationでも共通する進め方を説明する．

## テスト駆動開発のサイクル

TDDでは，次の3つの段階を短く繰り返す．

1. Red：まだ満たしていない振る舞いを1つだけ選び，それを確かめるテストを書く．テストを実行し，失敗することを確かめる．
2. Green：そのテストを通すための，いちばん簡単なコードを書く．テストを実行し，すべてのテストが通ることを確かめる．
3. Refactor：テストが通ったまま，重複を取り除いたり名前を直したりして，コードを整える．

Redで「失敗すること」を確かめるのには理由がある．
書いたテストが最初から通ってしまうなら，そのテストは何も確かめていないか，確かめたい振る舞いがすでにできている．
どちらの場合も，テストを書き直すか，別の振る舞いを選ぶ．

まだ存在しない関数をテストで呼ぶと，型検査やテストの実行が，関数が見つからないという理由で失敗する．
そのときは，型を書いたシグネチャと`throw new Error("TODO")`だけの関数を用意し，テストが「期待した値にならない」ことで失敗するのを確かめてから実装に進む．

## テストリスト

テストリストは，これから書くテストの一覧である．
実装を始める前に，要求を読んで思いつくテストを箇条書きにしておき，TDDのサイクルを回すたびに1つずつ消していく．

このハンズオンでは，各Iterationの資料に仕様書はなく，「要求」と使い方の例だけが書いてある．
要求を満たしたと言えるのはどういうときかを，自分でテストリストとして書き出す．
書き上げたテストリストと，そこから育てたテストが，そのIterationの仕様になる．
テストリストを書いたら，その振る舞いをどんな型・関数・モジュールで作るかを設計書に描いてから，実装に入る．設計書の書き方は[design.md](design.md)で説明する．

### 書く場所と形式

各パッケージの`TESTLIST.md`に，単体テストと結合テストに分けて書く．
次の例は，摂氏の温度を華氏に変換するプログラムのテストリストである．

```markdown
# テストリスト

## 単体テスト

- [ ] `toFahrenheit`：0℃なら32℉
- [ ] `toFahrenheit`：100℃なら212℉
- [ ] `formatLine`：「20℃ = 68℉」の形にする

## 結合テスト

- [ ] `run`：引数の温度を1行ずつ変換して表示する
- [ ] `run`：引数がなければ使い方を表示する
```

- 1行に1つの振る舞いを書く．「どの関数に」「どんな入力を与えると」「どうなるか」がわかるように書く．
- 具体的な値まで決めなくてよい．値はテストを書くときに決める．
- テストを書いて通したら`- [x]`にする．
- 作業の途中で新しいテストを思いついたら，すぐにリストに足す．いま取りかかっているテストを通すまでは，足したテストには手を付けない．
- やってみて不要だとわかった項目は，取り消し線(`~~…~~`)で消す．

### 単体テストと結合テストに分ける

どのパッケージも，テストを2種類に分ける．

- 単体テスト(`test/unit/`)：1つのモジュールの関数を単独で呼び，その関数の振る舞いを確かめる．境界の値や細かい場合分けは，ここで確かめる．
- 結合テスト(`test/integration/`)：プログラムの入口(`src/app.ts`の`run`)を呼び，複数のモジュールを組み合わせたときの振る舞いを確かめる．利用者から見た使い方の例が，そのまま結合テストの候補になる．

同じ振る舞いを両方で細かく確かめる必要はない．
たとえば確率の表示の細かい場合分けは単体テストで確かめ，結合テストでは「判定の結果が表示される」ことを1つの例で確かめれば足りる．
テストリストを書くときは，項目ごとに，どちらのテストで確かめるのがよいかを考える．

### 判断エンジンを使わずにテストする

`triage`は，判断をSystem Oneのサーバ(Ollama)に任せる．
しかし，テストではサーバを使わない．次の2つの理由による．

- モデルの答えは，入力の文章が同じでも，モデルの版によって変わりうる．テストの結果がモデルに左右されると，自分のコードの誤りなのか，モデルの答えが変わったのかを区別できない．
- 通信には時間がかかる．TDDでは何度もテストを実行するので，テストは一瞬で終わるほうがよい．

そこで，テストでは判断エンジンとの通信を，決まった答えを返す偽物に差し替える．
差し替え方は，それを初めて使うIterationの解説で説明する．
モデルが実際にどう答えるかは，テストとは別に，`pnpm start`やcurlで確かめる．

### 順番の選び方

テストリストのどの項目から始めてもよいが，次の順に選ぶと進めやすい．

1. いちばん簡単な場合(確率が0や1のとき，選択肢が1つのときなど)．
2. 少しずつ複雑な場合(しきい値の前後，選択肢が複数のときなど)．
3. 誤った入力など，例外的な場合．

結合テストは，それを通すのに必要な単体の部品ができてから取りかかるとよい．

## 実装の進め方

Greenの段階では，次の3つのやり方を使い分ける．

- 仮実装(Fake It)：テストの期待値をそのまま返す．たとえば`return "refund: yes (0.90)"`．テストが本当に失敗から成功に変わるかを，最小の手間で確かめられる．
- 三角測量(Triangulation)：仮実装では通らない2つ目の例をテストに足し，一般的な実装に書き換えざるをえない状況を作る．
- 明白な実装(Obvious Implementation)：実装がすぐにわかるなら，そのまま書く．テストが失敗したら，仮実装に戻して一歩ずつ進める．

## テストの実行

テストはVitestで実行する．パッケージのディレクトリ(`iterations/iteration-N/exercise`など)で，次のコマンドを実行する．

```sh
pnpm test                      # 単体テストと結合テストの両方
pnpm test --project unit       # 単体テストだけ
pnpm test --project integration  # 結合テストだけ
pnpm test test/unit/refund.test.ts  # 1つのファイルだけ
pnpm typecheck                 # 型検査
```

`pnpm test`は，テストを1回実行して終わる．
ファイルを保存するたびにテストを実行し直したいときは，`pnpm vitest`で監視モードにする(`q`で終わる)．
