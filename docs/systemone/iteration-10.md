# Iteration 10：比べ方と，確信度の較正

Iteration 10で初めて使う評価の考え方と，モデルを替えるときに使う設定・APIを説明する．
コマンドの例は，devcontainerの中で実行した実際の結果である．

## 同じデータで比べる

質問の文やモデルを替えたら，替える前と後で記録を取り，指標を比べる．
比べるときは，次をそろえる．

- 同じデータ：違うデータで測った正解率は，比べられない．Iteration 9では，質問を何も変えていないのに，`dev`の0.96に対して`test`は0.88だった．データが違うだけで，これだけ差が出る．
- 同じしきい値：正解率は，しきい値で変わる．ただし，確信度の出方が違う2つのモデルは，同じしきい値でも人の確認に回る割合が違う．その場合は，しきい値0(すべてを自動で振り分ける)でも比べるか，Iteration 7のしきい値ごとの表で，同じ割合を人の確認に回したときの正解率を比べる．
- 同じ環境と時間帯(所要時間を比べるとき)：所要時間は，CPUの割り当てなどで変わる．このハンズオンの開発環境では，同じ設定で記録を取り直しただけで，`tev1:0.8b`の中央値が0.4秒から2.8秒の間で変わった．比べる記録は，続けて取る．

同じデータで比べると，問い合わせごとに突き合わせられる．
この比べ方を，対応のある比較という．
正解率の差だけでなく，「どの問い合わせで答えが変わったか」を読める．

## 片方だけが正解した件数を数える

2つの記録を突き合わせると，問い合わせは4つに分かれる．

| | Bが正解 | Bが誤り |
| --- | --- | --- |
| Aが正解 | 両方正解 | Aだけ正解 |
| Aが誤り | Bだけ正解 | 両方誤り |

正解率の差を作っているのは，「Aだけ正解」と「Bだけ正解」の件数だけである．
両方正解・両方誤りの問い合わせは，どちらを選んでも結果が変わらない．

では，「Aだけ正解が0件，Bだけ正解が3件」なら，Bのほうがよいと言えるか．
AとBに本当は差がなく，食い違った問い合わせがたまたまどちらかに転ぶとする．
その場合，3件がそろって同じ側に転ぶ確率は，コインを3回投げてすべて表かすべて裏になる確率と同じである．

```console
> 2 * (1 / 2) ** 3
0.25
> 2 * (1 / 2) ** 6
0.03125
```

3件なら，差がなくても4回に1回は起きる．6件なら，32回に1回である．
片方だけが正解した件数が少ないうちは，差があるとは言い切れない．
この考え方は，符号検定(またはMcNemar検定)と呼ばれる比べ方のもとになっている．
件数を増やすほど，小さな差も見分けられるようになる．

## 調整用のデータで測った精度は高く出る

Iteration 9で，データを調整用(`dev`)と確かめ用(`test`)に分けた．
`dev`の誤りを読んで質問の文を直すと，`dev`の正解率は上がる．
その直し方が`dev`の問い合わせにだけ合っていても，`dev`の正解率は上がってしまう．
直したあとの実力は，直すのに使わなかった`test`で測る．

`test`を何度も測って直すと，`test`も調整用になってしまう．
`test`で測るのは，直し終えたあとの一度だけにする．
もう一度直したくなったら，`dev`に戻って直し，新しい確かめ用のデータを用意するのが理想である．

## 確信度の較正

確信度が0.9の答えは，10回に9回正しいのだろうか．
確信度と，実際の正解率が一致していることを，「較正がとれている」という．

較正を確かめるには，確信度を区間に分け，区間ごとに実際の正解率を求める．

```text
confidence  tickets  mean confidence  accuracy
0.0-0.2           1             0.07      0.00
0.2-0.4           5             0.29      0.80
0.4-0.6           3             0.52      0.67
0.6-0.8           6             0.72      1.00
0.8-1.0          15             0.95      1.00
```

これは，Iteration 10で説明文を調整した`tev1:0.8b`の，`test`での表である．
確信度0.2〜0.4の5件は，確信度の平均が0.29なのに，正解率は0.80である．
Ollamaの確信度は，確率の分布がどれくらい1つの選択肢に集まっているかを表す値で(Iteration 4)，正しい確率ではない．
そのため，確信度の値だけを見て「0.3なら3割しか当たらない」と考えると誤る．
しきい値は，確信度の意味から決めず，このような表や，Iteration 7のしきい値ごとの評価で決める．

区間ごとの件数が少ないと，正解率は大きく揺れる．1件の区間の正解率は，0か1にしかならない．
件数も一緒に読む．

## 精度と速さ

大きいモデルは，判断が正確になることが多いが，遅く，メモリを多く使う．
`tev1:4b`は，`tev1:0.8b`の約5倍の大きさ(約4.5GB)で，devcontainerのCPUでは1件に15秒ほどかかった．
1件あたり15秒では，1日に1000件の問い合わせを振り分けるのに4時間かかる．
精度の差が，その時間とメモリに見合うかを，記録の指標で判断する．

## モデルを取得する

devcontainerを開くと，Ollamaは`tev1:0.8b`を取得する．
ほかのモデルは，Ollamaの`POST /api/pull`で取得する．
`"stream": false`を付けると，取得が終わるまで待ち，終わったら1行を返す．

```console
$ curl -s http://ollama:11434/api/pull -d '{"model": "tev1:4b", "stream": false}'
{"status":"success"}
```

`tev1:4b`は約4.5GBあるので，初めて取得するときは時間がかかる．
`"stream": false`を付けないと，取得の進み具合を1行ずつ返す．

```console
$ curl -s http://ollama:11434/api/pull -d '{"model": "tev1:4b"}'
{"status":"pulling manifest"}
{"status":"pulling 35f9281a3df5","digest":"sha256:35f9281a3df58b566b24091572467001906a5a6aac879fe8005c4db19c8d4a2e","total":4482403072,"completed":4482403072}
…
```

`tev1:4b`を動かすには，Dockerに5GBほどのメモリを割り当てる．
devcontainerのOllamaは，一度に1つのモデルだけを読み込む．モデルを替えると，前のモデルを外してから読み込むので，最初の1件は時間がかかる．
使うモデルは，`.env`の`SYSTEMONE_MODEL`で替える．

## タイムアウト

SDKは，判断エンジンの答えを10秒まで待つ．10秒を過ぎると，その問い合わせをあきらめ(`APITimeoutError`)，少し待ってから送り直す．
送り直しは2回までで，3回とも間に合わなければ，`APITimeoutError`を投げる．

1件に15秒かかる`tev1:4b`では，最初の問い合わせが間に合わない．
ところが，判断エンジンは，SDKがあきらめた問い合わせの推論も最後まで続ける．
Ollamaのログを見ると，1件を振り分けただけなのに，同じ問い合わせが2回届いている．

```text
[GIN] 2026/10/08 - 13:26:24 | 200 | 15.221955457s |       127.0.0.1 | POST     "/v1/systemone"
[GIN] 2026/10/08 - 13:26:27 | 200 |  7.831855212s |       127.0.0.1 | POST     "/v1/systemone"
```

2回目が速いのは，1回目に読んだ問い合わせの続きを，Ollamaが使い回したからである．
たまたま答えは返ったが，判断エンジンには余計な仕事をさせている．
遅いモデルを使うときは，待つ時間を延ばす．

`TypeSafeClient`の`timeout`に，待つ時間(ミリ秒)を渡す．

```ts
const client = new TypeSafeClient({ baseURL, apiKey, defaultModel: "tev1:4b", timeout: 60_000 });
```

待つ時間は，コードに書かず，環境変数(`SYSTEMONE_TIMEOUT_MS`)で渡す．
モデルや判断エンジンによって適した値が違うのは，URLやモデル名と同じだからである(Iteration 5)．

### 省略できる設定をオブジェクトに入れる

このリポジトリの型検査は，省略できるプロパティ(`timeout?: number`)に`undefined`を入れることを許さない(`exactOptionalPropertyTypes`)．
値があるときだけプロパティを足すには，条件演算子とスプレッド構文を組み合わせる．

```ts
const options = { baseURL, apiKey, ...(timeoutMs === undefined ? {} : { timeout: timeoutMs }) };
```

`timeoutMs`が`undefined`なら空のオブジェクトを広げるので，`timeout`は足されない．
